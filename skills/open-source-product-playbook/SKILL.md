# 开源产品方法论（Open Source Product Playbook）

一套通用、与具体产品无关的方法论，覆盖从选题到发布到维护的全链路。**本 SKILL.md 只做路由与硬约束，细节按需读取 references/，不要一次性全读。**

## 0. 先定阶段，再读对应文档

| 阶段 | 用户诉求信号 | 读取 |
|---|---|---|
| 理念与选题 | 没头绪、找想法、评估想法值不值得做 | `references/MANIFESTO.md`（§3 评分卡 + §6 工作流） |
| 技术选型 | 用什么栈、Web 还是原生、包体积/性能权衡 | `references/TECH-STACK.md` |
| 设计系统（可选轴） | 用 MD3 / Fluent / Liquid Glass、界面气质、token | `references/UI-DESIGN.md` |
| 产品完善性 | 还缺什么才算完整、引导页/权限/更新/关于/社区 | `references/PRODUCT.md` |
| AI 协作与知识交付 | 怎么写给 AI 读的规范、评估、平台特性纪律 | `references/DEV-TIPS.md` |
| 项目落地约定 | 写/维护项目 AGENTS.md、交付流程、Git 安全 | `references/AGENTS.md`（元指南 + 模板） |

只读当前阶段需要的那一份。跨阶段推进时再读下一份。

## 1. 从零到一工作流（MANIFESTO §6 摘要）

门与门之间不许跳，每阶段有产出物。

1. **向外找真理**：不问用户「你的兴趣/技能栈/能投入多少时间」——只找自己适合的东西永远找不到真理。主动搜索前沿浪潮与平台缺口（五个来源见 MANIFESTO §3）。一个人 + AI 就够，「需要团队」不构成否决。
2. **构思**：生成 5–8 个候选，用评分卡打分（满分 65，≥45 进验证，≥55 强候选），呈现 top 3，每个附一页 brief（理念/需求证据/差异化/极致点/截图概念/风险）。命中一票否决的直接淘汰并说明——必须有勇气说「这个想法不行」。
3. **验证**：搜竞品为什么没做到极致、需求信号、可行性、平台风险与退路。用户拍板后写一页 project brief。不跳过验证。
4. **建造**：选栈（TECH-STACK）→ 设计系统可选（UI-DESIGN）→ 垂直切片推进，每片完整可用不留 TODO → PRODUCT P0 全项 → DEV-TIPS 协作纪律。**传播单元先行**：最早做出那张 hero 截图，用它持续校准方向。
5. **发布**：README 转化结构（logo → 名称 → 一句话 pitch → badge → hero 截图/GIF → 一键上手）+ 按 MANIFESTO §5 渠道投放 + release。
6. **维护与增长**：MANIFESTO §7（triage 纪律、认可一切贡献、长期主义、burnout 边界）。

## 2. 不可让渡的硬约束

- **选题是天花板，完成度是入场券**。不做小痛点工具，只做整合需求或创造需求。demo 级完成度计划一票否决。
- **产出物默认英文**：README、仓库描述与 topics、项目文档、commit message、PR/Issue 标题与正文一律英文。本套文档以中文书写只是元文档的写作语言，**不构成产出语言依据**；仅当用户明确指定其他语言时切换，且只对该次指令生效。面向中文用户的 i18n 翻译件不受此限。
- **P0 缺失 = 产品不完整**（PRODUCT §9）。第三方许可清单是法律必需，不是可选。
- **设计系统是可选轴**，与技术栈正交，可以不选。不要为了「统一」强行套一个不适合产品形态的系统。
- **信任即功能**：无遥测默认、无广告、无 star-ware、无弹窗纠缠、数据可导出、发布附校验和/签名。
- **交付闭环**：Issue 先行 → PR 进 main（带 `Fixes #N`）→ CI 全绿才合并 → **只在合并后关 Issue**。CI 不得自动关 Issue；required check 写仓库真实 job id，不编造。无合并权限则开 PR + Issue 留链接 + 保持 open + 交接维护者。
- **不主动 commit/push/开 PR/开 Issue**，除非用户明确要求交付。只暂存明确路径；保留无关改动；main 不 force-push。用户覆盖默认规则仅当轮有效，且须在 PR/Issue 评论中记录。
- **验证诚实**：green CI ≠ 真机正确；工具声称完成不能代替验证；报告实际命令与结果。人类责任不可转移——AI 写的代码，提交者必须读懂、验证、负责。

## 3. 写规范本身的纪律（DEV-TIPS §1）

为项目产出任何给 AI 读的文档时：

- 只写模型会做错的三类内容：反模式、决策判据、项目特有约定。通用百科不写。
- 自包含、命令式、可判定。「注意性能」不是规则；「列表 >200 条必须虚拟化，CI 用 5000 条种子数据验证」才是。
- 渐进式披露：入口只放索引与路由，细节按需注入。
- 标注时效（截至日期 + Baseline 状态）；未证实的条目标 [待核]。
- 规则背后要有机器 gate，散文规则不被执行。
