# 怎样选一个值得贡献的仓库

用户指定项目时，检查它当前是否接受这类改动，以及目标能不能验证。需要自行寻找时，先看用户有过合并记录、熟悉产品或能拿到测试环境的项目，再搜符合用户领域和平台要求的候选。优先找实际有人使用的产品和能独立验证的工作。

| 判断的问题 | 看什么 |
|---|---|
| 项目活着吗 | 近期人类提交、发布、维护者对 Issue 和 PR 的实际回复。机器人批量更新或无关的最近 push 只算背景。 |
| 维护者会审什么 | 读最近和候选问题相近的社区 PR。看是否获得实质回复、什么改动被接受、拒绝是因范围不符还是项目没有维护人力。 |
| 有事可做吗 | 找一个具体问题，核对当前版本、复现资料、现有 PR 或认领，以及维护者有没有同意这个方向。尽量指出下一步应跑的验证。 |
| 能持续吗 | 核对许可、支持平台、外部凭据或服务、构建依赖和维护活跃度。推测不能替代实际验证。 |

比较提交机会时给候选用同一观察窗口，例如近 90 天。以已经结束的外部人类 PR 为样本，包含已合并和未合并就关闭的 PR。报告样本数、已合并数，以及已合并样本从打开到合并的中位时间。记录实际窗口与分页截断。排除明确属于机器账号及项目团队的 PR，身份无法确认时单独标明。样本少时给具体例子和定性判断。星标可用于发现项目。

例如，两个仓库里，一个近期只有机器人更新，近几次同类社区改动无人回应。另一个更新不频繁，但维护者刚复现了一个尚无 PR 的导入问题。这时更值得深查后者。若这个问题需要本机没有的硬件，说明缺哪项验证，继续找同仓库能验证的任务。

交付一份用户能做决定的候选表，给项目链接、活跃或审查证据、可做的一项工作、验证条件和主要代价。推荐最合适的一项。用户已允许直接挑选并开展贡献时，可以按授权推进。多会话确实在并行搜同一批项目时，可用[锁脚本](../scripts/claim-repo.sh)的 `seen OWNER/REPO` 避免重复核对。它会记住已看过的项目，后续搜同类仓库时仍会影响候选。
