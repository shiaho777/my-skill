# 开源仓库维护

目的是让真实用户的问题得到修复，让维护者有足够证据审查和合并。用户已指定仓库或 PR 时，从那里开始。

| 用户要做什么 | 做到哪里 |
|---|---|
| 维护指定项目，或继续贡献已有项目 | 先查看该项目里自己尚未处理的评审和失败检查。需要选新问题时，做一项能复现、符合项目方向、可以独立审查的改动。持续维护或约定数量时，在同一项目按约定推进。 |
| 寻找值得投入的项目 | 按[项目筛选办法](references/choose-a-project.md)列出有证据的候选，说明最推荐哪个和第一项可能做的事。发现项目的任务做到候选和建议。 |
| 检查 PR 是否可以发，或准备提交上游 PR | 就绪检查保持只读，报告能否提交、阻塞项和证据。获准提交时，按仓库要求发出或更新 PR，再跟进到用户指定的状态。 |
| 处理自己的 PR 收件箱 | 优先处理维护者要求的实际改动和可归因于本 PR 的 CI 失败。将需要维护者操作的事项写清楚。回复、推送、关闭或合并依用户授权进行。 |

## 选一个值得修的问题

读项目的贡献指南、PR 模板和近期合并的同类改动。核对 Issue 中的复现、预期行为、当前意见、认领和已有 PR。先确认问题在目标分支仍存在，以及本机能验证修复。上游方向不明确时，找维护者已有决定或先提出一个具体问题，按授权沟通。

优先修可复现的崩溃、数据损失、功能回归或给用户带来实际困扰的问题。构建或测试故障也可以是有效目标。记录复现输入、当前结果和修复后应有的结果。若环境本身就失败，先确认失败是否来自目标问题。已指定项目时说明验证限制，自选项目可以换一个有把握完成的目标。

## 从本地修复到上游评审

1. 开始修改或发布前，用[共享仓库锁](scripts/claim-repo.sh)对 GitHub 返回的规范上游仓库名执行 `claim OWNER/REPO`。`acquired` 可以开工，`owned` 用于继续本会话的原任务，已有其他会话占用时保留对方工作。完成、放弃或切换时用同一会话执行 `release OWNER/REPO`。
2. 新贡献从已核实的上游目标分支创建独立工作分支，保全工作区里无关的改动。现有 PR 的评审修复在原 head 继续，推送前核对远端分支有没有他人更新。检查 fork 和上游地址、base、head，以及是否已有同一主题的 PR。
3. 修复根因，一个 PR 解决一个可独立验证的问题。按风险补回归用例，运行项目现有检查，审核从 merge base 到 head 的完整 diff。PR 用项目的语言和模板说明触发条件、用户可见结果、验证和局限。Issue 关联、DCO 或签名按上游实际要求处理。[GitHub 开源贡献指南](https://docs.github.com/en/get-started/exploring-projects-on-github/contributing-to-open-source)
4. 评审后用同一个 PR 继续。核对当前 head 的 CI 与审批状态，旧提交上的未解决反馈按现在是否仍适用处理。未运行的检查单独标明。失败先区分改动造成的回归、已有故障和基础设施故障，按原因修正或报告。用户要求跟到合并时，处理可控问题并跟进，直到合并或确有需要维护者操作的阻塞。[GitHub CLI 检查说明](https://cli.github.com/manual/gh_pr_checks)

收尾给出结果、PR 链接、实际验证和当前状态。统计成果时，提交、开 PR、等待评审和已合并分别按实际状态报告。维护者明确拒绝该方向时结束该项并释放锁。
